# Contributing to CardPulse

This is how the team proposes, builds, reviews and ships changes.

## Branches

| Branch | Purpose | Who writes to it |
|---|---|---|
| `main` | Stable, presentable version. Only receives merges from `develop`. | Release pull requests only |
| `develop` | Integration branch where finished features come together and get tested. | Reviewed pull requests from feature branches |
| `feature/<short-name>` | One new feature, e.g. `feature/watchlist` | The person working on it |
| `fix/<short-name>` | A bug fix, e.g. `fix/search-empty-results` | The person working on it |

Rules:
- **Always branch off `develop`, never off `main`.**
- One branch = one feature or fix. Keep pull requests small enough to review in about 15 minutes.
- Nobody pushes directly to `main` or `develop`. Everything goes through a pull request.

## Workflow

1. **Propose.** Open a GitHub Issue with the *Feature request* or *Bug report* template.
   Discuss in the issue or in the group chat, and assign the issue to one person before work starts,
   so two people don't build the same thing.
2. **Branch.**
   ```bash
   git checkout develop
   git pull
   git checkout -b feature/<short-name>
   ```
3. **Build.** Commit in small steps with clear messages (see below). Push your branch whenever you like:
   `git push -u origin feature/<short-name>`.
4. **Stay current.** Before opening a pull request, bring in the latest `develop`:
   ```bash
   git checkout develop && git pull
   git checkout feature/<short-name> && git merge develop
   ```
5. **Open a pull request into `develop`.** Fill in the template, link the issue (`Closes #12`) and
   add a screenshot for any visible change.
6. **Review.** At least **one teammate** approves. The reviewer pulls the branch, runs it and checks
   the items in the template. The author fixes the comments and the reviewer approves.
7. **Merge.** The author merges after approval, using *Squash and merge*, then deletes the branch.
8. **Release.** When `develop` is stable (for example before a check-in or the final presentation),
   open a pull request from `develop` into `main`. The whole team takes a look before it is merged.

## The built site (`site/`)

`site/index.html` is generated by `pipeline/build.py` and holds all the data inline, so if two
branches both rebuild it, they will almost always conflict.

- In feature branches, **commit only source changes** (`web/`, `pipeline/`, docs). Don't commit `site/`.
- To preview your work, run `python pipeline/build.py` locally and open `site/index.html`.
  Then discard the generated files before committing: `git restore site/` (and `git clean -fd site/` for new images).
- After merges, the maintainer rebuilds `site/` on `develop` in a single commit.

## Commit messages

Short imperative summary, 72 characters or less, and a body when the reason isn't obvious:

```
Add 6M/1Y/All range buttons to price history

Monthly snapshots made the full chart hard to read for new sets.
```

## Never commit

- `data/` (raw API data, already in `.gitignore`)
- virtual environments, `__pycache__`, notebook checkpoints
- API keys, tokens or passwords. If a future data source needs a key, read it from an
  environment variable and document the variable name in the README.

## Repository settings (one-time, done by the repo owner)

- Create the `develop` branch on GitHub and make it the default branch for pull requests.
- **Branch protection** on `main` and `develop`: require a pull request, require 1 approval,
  and block force pushes.
- Add a `.github/CODEOWNERS` file with each teammate's GitHub username so reviewers are requested
  automatically, for example:
  ```
  # Everyone reviews everything by default
  *              @username1 @username2 @username3 @username4
  ```
